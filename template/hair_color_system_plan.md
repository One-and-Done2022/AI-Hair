# AIFace 发色系统重构方案

## 1. 方案摘要

本方案采用“双层发色体系”：

- 第一层保留当前项目已经接入生成链路的“抽象发色基调 + 染发工艺”体系，保证参数页易用、Prompt 稳定、模型可控。
- 第二层新增 `SOLUTOR` 专业色卡库，作为专业检索、展示、映射和后续配方扩展层，不直接替换现有发色主链路。

该方案的核心目标不是把专业色号硬塞进生成模型，而是建立一套“前端可选、后端可映射、后续可扩展”的专业发色系统：

- 普通用户先选通俗发色。
- 进阶用户可展开专业色号。
- 后端始终以“抽象发色 + 染发工艺”为主进行 Prompt 组装。
- `SOLUTOR` 色号提供更细颗粒度的专业语义、系列归属和颜色参考，但不直接决定底层模型主提示词。

## 2. 当前系统基线

当前项目后端已经存在两类可直接用于生图的发色数据：

- 抽象发色基调：`natural_black`、`blue_black`、`dark_brown`、`chestnut_brown`、`mocha_brown`、`honey_brown`、`ash_brown`、`linen_blonde`
- 染发工艺：`solid`、`highlight`、`earloop`、`balayage`、`gradient`

当前参数页已经支持：

- 发色基调选择
- 染发工艺选择

当前模板链路已经支持：

- 归一化发色选择
- 发色目录接口
- 发色锁定/目标/工艺 Prompt block 组装

因此，本次不应推翻现有体系，而应在其上增加专业色号映射层。

## 3. 总体架构

### 3.1 双层模型

发色系统拆为三个正交模块：

1. 抽象发色基调
2. 染发工艺
3. 专业色号

其中：

- 抽象发色基调负责模型友好表达，例如“冷棕、蜂蜜棕、亚麻金、蓝黑”。
- 染发工艺负责颜色分布方式，例如“纯染、挑染、挂耳染、巴黎画染、渐变”。
- 专业色号负责品牌级细节表达，例如 `5/72`、`IS/77`、`CZ/21`。

### 3.2 产品层级

前端默认展示：

- 发色基调
- 染发工艺

前端进阶展开区域展示：

- `SOLUTOR` 系列
- `SOLUTOR` 色号
- 色号对应的视觉示意、色系说明和映射结果

后端生成逻辑：

- 默认仍以抽象发色和工艺作为核心 Prompt 输入
- 专业色号仅作为补充上下文和参数记录
- 若选中了专业色号，则自动补全或校正抽象发色映射

## 4. SOLUTOR 数据设计

### 4.1 数据目标

把实体色卡册整理成“可检索、可视化、可扩展”的电子色号系统，而不是试图猜测跨品牌绝对标准。

每个色号记录应包含：

- 品牌
- 系列名
- 系列类型
- 色号
- 深度前缀
- 深度等级
- 主色调
- 副色调
- 来源图
- 毛束截图
- 视觉备注
- 估算色值
- 对现有抽象发色的映射
- 对工艺的建议
- 是否推荐进入生成链路

### 4.2 推荐字段

建议以 JSON 结构存储，字段如下：

```json

  "brand": "SOLUTOR",
  "series_name": "烟熏冷雾系列",
  "series_type": "cool_mist",
  "code": "5/72",

  "depth_level": 5,
  "tone_primary": "7",
  "tone_secondary": "2",
  "source_image": "solutor_sheet_03.jpg",
  "swatch_image": "solutor_5_72.png",
  "visual_note": "偏灰棕、轻微雾感、冷调",
  "hex_estimate": "#6B5C53",

```

### 4.3 系列组织方式

建议先按以下维度组织：

- 常规色系
- IS 多段统一
- 经典盖白
- 经典青系列
- 冷雾莹彩系列
- 烟熏冷雾系列
- 迷雾清透系列
- 基色
- 工具色系
- 底色对照卡

其中：

- `基色` 和 `工具色系` 主要用于专业参考与后续配方扩展，不建议直接暴露为默认生图发色入口。
- `底色对照卡` 作为对照展示数据，不作为普通可选色号。

## 5. 抽象发色映射策略

### 5.1 保留当前八类抽象发色

第一阶段保留以下 8 个抽象发色不变：

- `natural_black`
- `blue_black`
- `dark_brown`
- `chestnut_brown`
- `mocha_brown`
- `honey_brown`
- `ash_brown`
- `linen_blonde`

原因：

- 当前前后端已接通
- Prompt 已验证
- 对普通用户更友好
- 适合作为专业色号的统一落点

### 5.2 映射原则

每个 `SOLUTOR` 色号都要映射到：

1. 一个主抽象发色
2. 一个或多个推荐染发工艺
3. 一个温度标签
4. 一个深浅桶位
5. 一个生成友好别名

映射原则如下：

- 偏黑冷色映射到 `natural_black` 或 `blue_black`
- 深棕暖棕映射到 `dark_brown`、`chestnut_brown`、`mocha_brown`
- 浅棕暖米色映射到 `honey_brown`
- 冷雾灰棕类映射到 `ash_brown`
- 高明度奶金、亚麻金映射到 `linen_blonde`

### 5.3 工艺建议

专业色号不只映射基调，还要映射推荐工艺：

- `solid`：纯染、全头色统一
- `highlight`：线条挑染
- `earloop`：挂耳染、耳圈染
- `balayage`：巴黎画染、空气感分布
- `gradient`：发尾渐变、层级色差

例如：

- 冷雾灰棕适合 `solid`、`balayage`
- 高对比个性色适合 `highlight`、`earloop`
- 高明度浅色适合 `solid`、`gradient`

## 6. 参数页交互方案

### 6.1 默认交互

参数页第一层继续保持当前使用习惯：

- 先选发色基调
- 再选染发工艺

### 6.2 进阶入口

在发色模块增加“展开专业色号”入口，点击后展示：

- 系列筛选
- 色号搜索
- 色卡网格
- 色号详情抽屉

### 6.3 用户选择逻辑

用户操作建议采用以下流程：

1. 先选择抽象发色
2. 可选地展开 `SOLUTOR` 专业色号
3. 选择某个色号后：
   - 自动高亮其映射的抽象发色
   - 自动展示推荐工艺
   - 自动写入草稿中的专业色号字段
4. 若用户后续改动抽象发色，则专业色号进入“参考状态”或清空

### 6.4 参数存储

草稿中建议新增但不替换现有字段：

- `hair_color_professional_brand`
- `hair_color_professional_series`
- `hair_color_professional_code`
- `hair_color_professional_note`
- `hair_color_professional_hex_estimate`

保留现有字段：

- `hair_color`
- `hair_color_technique`

这样可以保证：

- 老接口不炸
- 老页面可兼容
- 新功能可渐进接入

## 7. 后端生成策略

### 7.1 Prompt 组装原则

生成链路继续遵循“抽象发色优先，专业色号补充”的策略。

建议的 Prompt 逻辑：

- 主发色描述来自 `hair_color`
- 工艺描述来自 `hair_color_technique`
- 若存在专业色号，则只追加柔性补充语义，如：
  - 冷雾感
  - 偏灰棕
  - 轻奶茶调
  - 低饱和烟熏感

不建议把 `5/72`、`IS/77` 这类编号直接进入最终生图 Prompt 的主干。

### 7.2 颜色污染控制

发色语义应单独作为 hair block 控制，避免污染服饰、背景和肤色。

建议：

- 保持独立 hair color prompt block
- 对工艺增加局部范围限制语义
- 冷暖色描述与服饰色描述隔离

### 7.3 生成友好级别

建议给专业色号增加“是否适合直接参与生成”的布尔字段：

- `true`：可参与生成补充语义
- `false`：仅用于展示、参考、配方扩展

以下类型建议默认不进入生成：

- 纯工具色
- 纯盖白技术向色号
- 依赖底色和双氧条件强的色号
- 实体观感与模型理解差距过大的色号

## 8. 电子色盘工具设计

### 8.1 MVP 目标

先做一个轻量级色盘工具，用于：

- 按系列浏览
- 按色号检索
- 查看局部毛束截图
- 查看估算色值
- 复制色号和 HEX
- 为后续配方功能留扩展位

### 8.2 页面结构

建议页面包含五个区块：

- 顶部搜索栏
- 系列 Tabs
- 色卡网格
- 详情抽屉
- 工具区

色卡卡片展示：

- 毛束局部图
- 色号
- 系列名
- 估算色块
- 映射后的抽象发色

详情抽屉展示：

- 色号拆解
- 系列信息
- 视觉备注
- HEX/RGB/HSL
- 底色参考
- 相近颜色推荐

### 8.3 技术形态

MVP 可先采用：

- HTML + CSS + JavaScript
- 原生 `<input type="color">` 做辅助取色
- JSON 数据源

进阶版可升级：

- 使用 `iro.js`
- 支持 HEX / RGB / HSV / HSL 同步查看
- 支持颜色拖拽比较和人工校色

## 9. 数据落地节奏

### 阶段一：数据整理

- 整理 `SOLUTOR` 全系列基础 JSON
- 建立统一字段规范
- 完成色号去重、排序和系列归类
- 补齐 `hex_estimate`、`visual_note`、`keywords`

### 阶段二：映射层接入

- 为每个色号补充 `mapped_tone_id`
- 为每个色号补充 `mapped_technique_ids`
- 标记哪些色号适合参与生成
- 提供专业色号目录接口

### 阶段三：参数页接入

- 参数页增加“展开专业色号”入口
- 支持搜索、筛选、预览、选择
- 选择后同步回抽象发色和工艺

### 阶段四：生成链路增强

- 在模板服务中读取专业色号
- 以补充语义方式增强 Prompt
- 验证不同系列的生成稳定性

### 阶段五：专业工具扩展

- 增加色盘工具页
- 增加底色对照模式
- 预留配方查询和专业师端模式

## 10. 测试与验收标准

### 10.1 数据正确性

- 每个色号都能被唯一检索
- 每个色号都能定位到所属系列
- 非标准前缀如 `IS`、`G`、`CZ` 能被正确保留
- 工具色、基色、底色对照卡不会误入普通生成入口

### 10.2 参数页行为

- 默认用户仍可只选抽象发色和工艺完成流程
- 展开专业色号后可按系列筛选
- 可按 `5/72`、`72`、`冷雾`、`盖白` 等关键词搜索
- 选择专业色号后，抽象发色映射正确
- 修改抽象发色时，专业色号状态可控且不冲突

### 10.3 生成链路

- 未选择专业色号时，原有生成效果不回退
- 选择专业色号时，生成 Prompt 不出现硬编码编号污染
- 同一抽象发色下，不同专业色号能带来轻度风格差异
- 发色语义不会明显污染背景、服饰或妆造

### 10.4 可扩展性

- 数据结构可继续接配方字段
- 页面结构可继续接底色对照与收藏导出
- 后端接口扩展时不破坏现有参数协议

## 11. 默认决策

本方案默认采用以下决策：

- 保留现有 8 个抽象发色，不直接替换
- 保留现有 5 个染发工艺，不额外拆新工艺
- `SOLUTOR` 作为第二层专业系统接入
- 参数页优先使用“先选抽象发色，再展开专业色号”的交互
- 第一阶段先服务参数页接入，不先做独立后台系统
- 生成链路以抽象发色 + 工艺为主，专业色号只做补充上下文

## 12. 后续实现建议

如果进入正式开发，建议按以下顺序推进：

1. 先补 `SOLUTOR` 数据源和映射字段
2. 再补后端 catalog / schema / 归一化逻辑
3. 再改参数页交互
4. 最后接生成链路增强和色盘工具

这样可以最大限度保证：

- 老功能不断
- 新系统可灰度接入
- Prompt 稳定性优先
- 专业体系与 C 端体验同时兼顾
